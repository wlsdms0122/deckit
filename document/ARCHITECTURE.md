# How deckit is built

Deckit is a library a host app embeds to take mods. A mod is what a person adds to the host app, as to a game: a view, a command, a few keys, a way to open an address, exports for the mods that depend on it, a new look, or work done in the app's main process, in any mix.

Deckit is three layers, each built on the one under it:

| Layer | What it is | As an operating system has it |
|---|---|---|
| deck | the engine: what a mod is, running each in a sandbox of its own, what mods give each other (dependencies and their connections, events), their storage and the place each layer above keeps for each mod, and the permissions a person grants | the kernel |
| deckit | the platform on deck: a mod's function lifecycle (`start`, `stop`), its configuration, web sessions, keys, commands, opening addresses, the clipboard, notifications and main process modules, and `connect`, which a host app starts it with on the environment it runs on | the operating system: what an application runs on, on this machine |
| the shell | the surface a person uses deckit through. Deckit's own shell is the panel, which lists the mods with a view and lends the one in front room beside and under its list, a mod's window, the web pages a mod shows, the kit they draw with, and styles, and it stacks a mod's screen lifecycle (`attach`, `detach`) on deckit's; deckit runs its mods whether or not a host app puts it on, so a host app may leave it off | the system's interface, as macOS has its menu bar, its Dock and the windows apps draw in |

A mod is an application. The host app is the machine: the process and its windows. It makes the environment deckit runs on, starts deckit on it, puts a shell on it, and says where the shell is shown. Deck knows nothing of a screen: to deck a mod's page is where the mod runs. Deckit knows no shell: the shell is built on what `connect` answers, as a host app's own would be. A mod runs whether or not the panel is shown, and whether or not a shell draws it: what it does is registered in deckit's lifecycle, and what it shows in the shell's, stacked over it (MOD.md, Lifecycles). A lower layer holds only the questions its own mechanism asks, and the layer above answers them: deckit's keymap asks whether a page is in front, and the shell answers.

This document is why deckit is split the way it is, and the rules that keep it so. The contract a mod is written against is [MOD.md](MOD.md); how a host app embeds deckit is [EMBEDDING.md](EMBEDDING.md); the kit mods draw with is [UI.md](UI.md).

## 1. Principles

1. Deckit is whole by itself. `source/deckit` and the documents it ships (EMBEDDING, MOD, UI) are all of it, and name nothing outside it. The package around it is for convenience: its commands check, build, run and ship deckit, with whatever tools serve.
2. A mod can do what the host app can. Permissions say what a mod reaches, and the person agrees to them; none is a dead end, and a main process module has the app's full power. A mod draws its view as it likes; the kit is the quick way, not the only one.
3. Deckit owns only what it makes. The process, its menus and its windows are the host app's; deckit is handed what it needs through `connect()`: the environment, the app's answers and its configuration.
4. A check happens once, where trust changes: main receiving from a page, deck receiving from a mod's code, input from the disk or the network. Inside, each step trusts what the step before it made.
5. A fact has one owner. Everyone else asks it.
6. A layer adds to the one under it and is not known by it: what it gives a mod, what a mod registers with it, the permissions that grant it and the manifest fields it reads, it adds there.
7. A folder is a module or a group, named for its concept. Folders beside each other use each other one way, never back, directly or through others; what is in a folder uses what the folder may, and never the folder that holds it. A name is the standard term of its field, one name for one act: to reveal is to make something visible where it lies (a file in Finder, an entry in a tree), to show is to bring a view to the front.
8. The packages' names (deckit, deckit-electron, deckit-shell) are the code's; deckit is deck and deckit in Swift, deckit-electron is the environment deck and deckit run on in Electron, and deckit-shell is deck and deckit in JavaScript with the shell on them, which declares what an environment gives it. Deckit is also the product's name, and what goes outside keeps it: the scheme `deckit://`, the `[deckit]` tag, the archive, the default id, and the `deckit.*` permissions, which reach inside the app as `system.*` ones reach past it.

Each is a package of its own. One reaches another only through what that one hands out: its entries, or what it answers at run time.

The package around deckit, `manifest.toml` and `source/cli`, is the commands that check, build, run and ship it (README.md). Deckit names none of it.

A new mod needs no change to deck. A new place to show the panel in needs no change to deckit, and a shell of the host app's own needs no change to deckit.

## 3. Processes and pages

| Where | What runs there |
|---|---|
| the core | deckit's own process, the host app's child: the mods it reads and installs, which of them run and where each run is, what they store, and the state |
| main | deck: the mods, their runs and the state as the core gave them, the pages the mods run in, and what a page asks of deck. Deckit: main process modules, the keymap, opening addresses, commands, configuration, the web. The shell: the panel, a mod's window, the views it puts in the host app's windows. A mod with a window fills it with its page |
| a mod's sandbox | where one mod's entry runs, headless or not: a page in a `WebContentsView` of its own at `deckit://<id>.mod/`; with deckit's shell on deckit, a mod with a view lays it there where the panel's frame leaves it room, or in a region where it is another's child |
| a page that runs no mod | made for the shell, at `deckit://<name>/`: the panel's frame, at `deckit://panel/`, with the two documents it opens and draws in, its backdrop under the mods and its width's handle over them |

A mod's sandbox is a renderer and deck is in main. Each mod's sandbox has its own origin, its own sessions and its own storage, so one mod cannot reach another's page, data, cookies or what it was allowed; a mod with `deckit.styles` styles another's page, and that is all. Main knows which mod is asking by the page that asks (`deckit-shell/deck/identity`): no page says who it is. A mod's page is held to its origin; a link out of it is offered to its scheme's handlers.

The pages never speak to each other. Main carries everything between them, and every word is a channel declared once in its concept's `protocol.js`, named for its package (`deckit-electron:`, `deckit-shell:`), as `deckit-shell/deck/channel` declares one: `pageToMain` for what a page asks or tells main, `mainToPage` for what main tells or asks a page. A declaration is plain data. `deckit-shell/deck/ipc` binds it, a side each (`main.js`, `renderer.js`), and every channel crosses as a message carrying its channel's name (`deck/ipc/model/envelope.js`), which the environment carries: `deckit-shell/environment` says what an environment gives deck, and Electron carries the messages over the few channels of its IPC in `deckit-electron/messages/protocol.js`, so Electron's IPC knows only those. A question main asks a page and the page's answer go as tells, told apart by the id they carry. A page is a token deck keeps and hands back and never reads; in Electron it is the page's webContents. Binding reads a declaration once and keeps it, so a channel is declared once: binding the same declaration again binds the same channel, and another declaration of its name is refused. A channel is heard once something answers or listens on it, and is answered once. Deck's concepts bind their own as their modules are imported, with `ownChannels`; the shell binds its own with the `channels` it is handed (`layerChannels`), as it is attached and as a page starts it, never under a name deck binds as its own. What carries the channels is handed to each side once, before anything crosses: in main as `connect` starts, on a page as it boots. A question main asks a page is heard from the page's start and waits there for the page's code to say how to answer it, for as long as main waits. A page asking what main does not answer, sync or not, gets an error back, and what a page tells that nothing in main listens on is logged as refused. What main tells a page before the page listens is not kept: a page reads what is so as it starts, and what main told before would come after that. Main holds what arrives to the channel's fields; nothing else checks it. A question main asks a page ends when it is answered, when the page goes away, or when its time runs out. An error crosses with its kind.

The core is `source/deckit/deckit`, a Swift package: `Deck` and `Deckit` on `Deck`, two libraries, and `DeckitServer`, the executable `deckit`, which answers through `Deckit`. It reads the mods and installs them, judges a mod's configuration against what its run declared, judges what mods reach of each other, keeps the keymap, and keeps a mod's records, its data folder, the places the layers above keep for it (the values of its configuration), and the state: main asks for a mod's as its page does, and the core answers by the mod main names. A manifest is read against the mod contract main runs mods with and the permissions the layers on deck defined, which main hands the core as it starts, and with the fields deckit adds (`Deckit`). Main reads the mods once the core has installed what the app ships, and again after what changes them, installing or removing, which only main asks for; what asks at once is answered from that copy. Main reads the state once, before anything on deckit reads it, and answers each read from that copy at once. Main writes the state but for the mods removed with their data still to erase, which the core keeps itself, and the core keeps writes in the order sent, so a write goes to the copy and to the core; one the core refuses is taken back out of the copy. `Deck` and `Deckit` are libraries a Swift host uses as they are, taking and answering Swift's own types: deck's parts (`records`, `modState`, `catalog`, `dataFolder`, `storage`, `erasure`, `connections`, `events`, `state`), deckit's (`keymap`, `commands`, `urlRouter`, `configuration`), and `Deck` itself for what reads the catalog again and what moves the runs. What is on the wire is the server's (`DeckitServer/Server`): each method's name and params, how each answer is written, a refusal's kind, and the name of what a layer tells has changed (`LayerChange`), which deck carries and does not read. A form stays with its type only when a mod writes it (a contribution, a configuration's declaration, a key) or the disk keeps it (a configuration's value, a chord a person gave, how they arranged a scheme's handlers); a form only main reads or writes is the server's. The state keys a part keeps itself (the mods to clear, the chords a person gave, the scheme handlers) are reserved, and a write of one is refused. A layer above deck reserves a name in `modState` the same way (`configuration`), and deck keeps a text for each mod under it, which it counts and erases with the mod and never reads.

The core loads and unloads the mods main names (`Deck/Run/Lifecycle`, `Deck/Run/Runner`): a mod runs only while what it requires runs, and ends before it. Main decides which load and when, and does what running them takes (`deckit-shell/deck/runner`): it loads every mod as the app starts, each once what it requires has launched, loads a mod found or changed again with the mods that require it, restarts one as asked, unloads them all as the app quits, and makes a mod's page, knows it as the mod's and sets it up before it loads it, asks it to end its lifecycles, closes it and hears it crash, each through what the environment gives deck of a page (`pages`: `make`, `load`, `close`, `watch`), which tells why a page's process ended, so a crash is told the core with its cause whichever of what watches the page hears it first. The app is held from quitting while a run has not ended (`app.onQuit`). Main asks the core to load or unload mods and tells it what happened, a run that started, did not start, crashed or stopped, a problem against a run, and the core answers what follows from it as effects, in order: a run's transition to keep and tell (`tell`), a problem kept (`keep`), a page to make (`open`) or load (`loadPage`), an end to ask (`stop`), and a sandbox to close (`close`). What comes of an effect, an end answered or timed out, comes back as what happened next, so the core never waits on main. The mods that load are those of the catalog as main last read it, so what runs and main's copy are one. Main keeps each run as the core last told it, one object for as long as the run lasts, with what it contributed (`summary`, `contributions`), which its page reported as it started and again as each lifecycle above the first joined (`runner/joined`), and the core keeps. The page tells too, once its entry is evaluated, what the layers read of the class (`runner/described`), and how many lifecycles it stacks, so main waits for each to end in its own time.

What mods reach of each other, the core judges (`Deck/Reach/Connection`, `Deck/Reach/Event`), and main carries (`deckit-shell/deck/connection`, `deckit-shell/deck/event`): which connections stand and whether a message on one goes, and which mods hear an event. Main sends what a message or an event carries from page to page itself, and never through the core. As a lifecycle of a run begins, its page asks main for its connections: main asks the core which stand (`connection/begin`) and asks the page of each dependency for its exports (`connect`). As the lifecycle ends, the page tells main, and main tells the core (`connection/end`). The connections that stand or end as runs move come after a runner's answer's effects (`connect`, `disconnect`), and main tells both pages. A message on a connection is judged by one question, whether the connection stands and the page that sends it is one of its ends (`connection/route`), and goes to the other end. A connection a dependency's page refused stays down while both its ends are up (`connection/refuse`). Of a run's connections the core keeps what it contributes: the lifecycle that opened its exports (`exportedIn`) and the lowest lifecycle that waits for each mod's (`awaits`), from which it warns of an `onConnect` the exports never reach.

Deckit in the core adds three layers to deck (`Layer`), the command registry's, the keymap's and the URL router's: each reads what a run contributed under its own keys and says what is wrong with it as the run starts, which is recorded against the run, and the keymap adds what of it has changed to a runner's answer. What a run contributes is read only from its launch until it has ended (`Deck.contributions(of:)`). The keymap is deckit's in the core (`Deckit/Keymap`): the keys the host app and its shell register, those each run contributes (`keys`, taken while it runs and as it terminates), the chords the person gave them, kept in the order given, and how a keystroke is resolved against them, each binding with its chord, its issues and the keystroke it answers to. Main keeps the keymap as the core last told it, after a runner's answer (`bindingsChanged`) or as the answer to a change it asked for, whichever came later by its `revision`, and resolves a keystroke against that copy where it lands, as the environment asks whether to take a key at once (`keys.capture`, `deckit-shell/deckit/keymap/main.js`), the narrowest scope first; a chord held in every app (`keys.hotkey`) lands in the page that has the keyboard (`keys.focused`), or runs with none. What a key typed to be bound comes to, the core says too. A run contributes its `commands` and whether it answers addresses (`urls`), and the host app and its shell register theirs under `@` names: `Deckit/Command` lists them and checks a command and its args before main runs it, the keymap checks each key's label and chord, a key's `run` stays in the page or the process that registered it, who a provider is the core answers (`Deckit.provider(of:)`), and the core answers where an address goes (`Deckit/Open`), which says too when a mod registers a URL handler and its manifest names no `urls`. What a scheme is, which are no place to open, and which addresses a pattern matches, is the core's alone.

Main starts the core once the app is ready, from the file the host app hands the environment as `core`, which the environment runs (`core.open`, in Electron `deckit-electron/core`), and asks nothing else of it until it has answered `initialize` with deckit's folder, the app's name, the mods it places in each scheme's handler list, the mod contract, the folders of the mods the app ships and of those read in place, and the permissions the layers defined. They speak JSON-RPC 2.0, a message a line: main's requests on the core's stdin and its answers on its stdout, and what it writes to stderr is deckit's log. The core answers one message at a time in the order they come, and asks main nothing. A refusal crosses with its kind, as between main and a page. How the messages go is `deckit-electron/core/connection.js` and `DeckitServer/Transport`; what they are, `deckit-shell/deck/core/message.js` and `DeckitServer/Server`. Deck's client of the core is `deckit-shell/deck/core/main.js`.

A core that ends is not started again. Main logs why, and refuses all that is asked of it after, saying the app is to be restarted, so whatever asked shows it: a mod's write that did not land, on its row in Settings. The core ends as its stdin does, when the host app's process ends, however that ends.

What a mod is, the core says (`Deck/Mod/Manifest`): its manifest, its folder, its permissions and its entry. `deckit-shell/deck/mod` holds what main runs mods by: the names of the lifecycle's notifications, the permissions deck checks, and how a name of a mod's is scoped; `deckit-electron/mod` the files of a mod's folder its page is served. They name nothing of running them. Some rules are in both, each where it is used, until what uses the JS one moves to the core: how a name of a mod's is scoped (the core's events, and a mod's page), what is inside a mod's folder (the core's entry, main's serving of files) and the names of the lifecycle's notifications (the core's effects, and what main hands the layers on deck before the core has started). Main's runner tells each transition of a run as the core told it (`willLaunch`, `didLaunch`, `didFailToLaunch`, `willTerminate`, `didTerminate`), and `didJoin` once a lifecycle over the first has joined, or failed and ended, which changes what the run contributes; what follows a mod's run above deck in main (its main process modules, its styles and its place in the panel) listens to those, or asks the run, and changes none of it but to record a problem. The core takes a run's configuration only while that run launches.

Deckit's folder is the `home` of the host app's `folders`, or `~/.config/<id>`:

```
deck.json       deck's settings: the load order (`loadOrder`), the mod ids
mods/           installed mods, a folder each, named by id
data/<id>/      a mod's own files (a main process module's notes, its workspaces)
records/<id>/   a mod's records, one JSON file a key
mod-state/<name>/<id>.json   what a layer above deck keeps for a mod, by the name it reserves (`configuration`)
state/          what the person arranged, and what deck and deckit keep between runs, one JSON file a key
state/host/     what the host app and its shell keep, one JSON file a key
logs/
```

The core lays out all but `logs/`, which is main's, and answers `initialize` with where it keeps the mods and the data folders, and each mod it reads with its own data folder (`data`), which main hands the mod's main process modules.

Everything deckit keeps is named from its configured id, so two host apps that embed deckit keep their data apart.

## 5. What a mod is handed

A mod reaches deckit only through its handles: `deckit`, which `start` and `attach` are handed, and `shell`, which only `attach` is (MOD.md). Before a mod runs, the page's preload puts deckit together, as the host app does in main: the environment's `boot` takes away every global the bundles added and answers what Electron gives the page, and the shell's `start` (`deckit-shell/renderer.js`) runs deckit on the page with it; the mod's entry runs with only `module` and `exports` in reach, as the environment evaluates it.

Deck evaluates the entry, and each layer reads the class it exports. Deck makes one instance of it and runs the lifecycles the layer on it stacks, the lowest first, each with handles of its own and a scope that cuts, as it ends, what its handles made that calls back into the mod's code. Deck knows neither how many lifecycles there are nor their names: it joins what each registered as its start ends, tells main the first as the run starting and each after as it joining, ends them the highest first, and fails the run only when the first fails. Each lifecycle is connected to the exports it reaches as it begins, before its method is called, and its connections end once its end method has run and what its handles made is cut. `exports` is registered once for the run, in whichever lifecycle has the job.

The handle `deckit` is deck's members and deckit's. Deck gives a mod its id and name, its storage, `dependencies`, `exports`, `events`, and with its permission `mods`. Deckit adds the function lifecycle, configuration, web sessions, the clipboard, notifications, who a provider is, main process modules and, with its permission, `modConfiguration`. It adds the namespaces `keys`, `commands` and `urls`, each with `register` for the mod's own and members that reach others', some behind a permission. On `mods` it adds picking and revealing mod folders and restarting, and it reads the class's `configuration` and `keywords`. The shell on deckit stacks the screen lifecycle and hands it the handle `shell`: the theme, the kit, `show()`, `region()`, `children`, `iconOf()`, `formOf()`, the web pages of a session, and with their permissions `fonts` and the panel's pins on `mods`, and `view`, `window` and `styles`, each with its `register`; it reads the class's `icon` and `form`. A layer's registrations are kinds deck does not know, and what a layer says of a mod (its summary and contributions) deck carries to main and does not read. What a layer gives a mod is never replaced by what a layer above it gives: a name a lower lifecycle registered stands, and the higher one's is left out.

Between mods there are two ways, and one question picks: could the host app do this if the other mod were not there?

- If it could not, it is a dependency. A mod names another in `[dependencies]`, required or optional, and is connected to the exports that one opens (below). A dependency nobody wrote down cannot exist. A required one is part of the mod: the mod loads after it and ends before it. An optional one comes and goes, and the mod hears it.
- If it could, it is a public relation: an address the mod asks to be opened (`deckit.urls.open(url)`) without knowing who answers, or a command it runs. The mods whose `urls` patterns match the address are its handlers and are asked in the order the person set, ahead of deckit's own answer, which is always last.

Apart from both, a mod says what happened to it through deck's events (`deckit-shell/deck/event`, judged by the core's `Deck/Reach/Event`): `deckit.events.emit(name)` is heard as `<its id>:<name>` by any mod that listens, and no mod speaks for another. Listening takes no dependency. A page's own listeners by name are `deckit-shell/deck/event/bus.js`. Public relations are open to anyone at any time, and the one who asks may be no page, so they carry values only: a function crosses only a connection, which has an end at which to let it go.

Deck has one device between mods' pages, `deckit-shell/deck/connection`. A connection stands between the exports a mod opened in one lifecycle and one lifecycle of a mod that depends on it, and ends as either ends (MOD.md, Dependencies and connections). It is built in three layers:

| Layer | What it does | What it does not know |
|---|---|---|
| the core, `Deck/Reach/Connection` | stands connections up and ends them, from the manifests' `[dependencies]` and the lifecycles up on both ends; judges a message by one question, whether the connection stands and the sender is one of its ends; tells both pages as a connection stands and as it ends | what crosses, and how many references there are |
| the wire, `deckit-shell/deck/connection/protocol.js` and `model/wire.js` | the shape of what crosses: `{ value, references }`, `value` JSON with each function left out, and `references` a `[path, number]` for each. The same shape carries exports, args and results. Three messages: `call` on a number, its answer (what it returns, or `{ name, message }` thrown), and `release` of a number | the language |
| the binding, `deckit-shell/deck/connection/renderer.js` | moves the language's values to the wire and back. For each connection it keeps a table of the functions it handed over, by number, and of the references it holds, by number, and drops both as the connection ends | the other mod's language |

A number is from the table of the end that handed the function over, and means something only on its connection: the same function handed twice on one connection is one number. Every call is a message, so every call is asynchronous. A reference received is never handed on, so whatever calls into a page is the mod connected to it.

The architecture is the same whatever language a mod's page runs: only the binding is language specific. A binding says which of its language's values are data and which cross as references, how a received reference is called and how it learns the page holds it no more, and how `dependencies.<id>` reads in that language. The JavaScript binding copies an object's own enumerable data, sends its functions and its class's methods as references bound to it, makes each number one function answering a promise, and learns of one held no more through a `FinalizationRegistry`.

A mod changes how another's pages look with styles, which the shell puts last on each page they style, and nothing else of another mod.

What reaches past a mod's own sandbox (the clipboard, notifications, any web address, handing a file on, a window over every app, another mod's configuration, other mods' commands, the keymap, other mods' looks, a main process module) is asked for by name in `permissions`, with a reason the person reads when installing. The names are the mod contract's: the host app's root hands the core every name the layers' models hold, and each layer on this host defines those it gives, before the core starts, and checks them where the mod asks, by the page it asks from. Deck's own are the core's, and so are `deckit.app-keys` and `system.global-keys`, which the core's keymap checks. A name the contract does not have stops the mod; one no layer on this host defines is not usable here (`usable` on the manifest's permission), and the mod runs without what it guards.

## 6. Modules

Deckit-electron and deckit-shell are each a package, and every file in them an ES module: it imports what it uses and exports what it is. Inside a package, each folder is one of its concepts, a module or a group of them: folders beside each other use each other one way, never back, directly or through others, what is in a folder uses what the folder may, and nothing uses the folder that holds it. A mod's `src/` and `main-process/` keep the same shape, with only the entry beside the concept folders in `src/`. A package uses the public surface of the packages it depends on, its entries, from any of its files, and nothing else of them. A package says in its `package.json` what it depends on and its entries (`exports`). Its root holds that file and the two that put it together, `main.js` and `renderer.js`, where it has them; everything else is a concept folder:

| Package | Its entries | What it depends on |
|---|---|---|
| `deckit-electron/` | `main.js`, `environment()` and `SCHEME`; `renderer.js`, `boot()`, the start of a page's preload, which answers what Electron gives the page; `contract/`, the version of the mod contract and the scheme, read with nothing of Electron's (the build reads them for `deckit.json`) | deckit-shell |
| `deckit-shell/` | `main.js`, `connect()` and `attach()`; `renderer.js`, `start()`, deckit on a page; and what an environment uses of it, as plain data: `environment/`, what an environment gives deck, on main and on a page, and a stage (`STAGE`), with `checked`, which holds a given object to one of these and answers a frozen copy of only what it declares, a member of the wrong kind counting as missing; `deck/contract/`, the mod contract's version; `deckit/web/model/`, how a mod's web session is named, a site's origin, and the permissions a site is asked for or given | nothing |

Deckit-shell's `deck/` is a group: deck's part, its concepts the folders in it, which use nothing outside it, so deck names nothing of deckit there. Deckit's concepts lie beside it and use what is in it; `deck/core/`, how main reaches the core, carries deck's configuration and deckit's in `initialize`. Deckit-electron's root makes the environment, and its folders are its parts, each beside the others. Deckit-shell's root puts deck's parts and deckit's together on it in `connect`: it holds the environment to what deck is given and configures it first, then makes deck's parts before deckit's.

In main the shell reaches deckit through what connect answers, handed to `attach` (`deckit-shell/api/`), as a host app's own would be. On a page deckit is the shell's: the preload hands `start` what `boot` answers the environment gives a page (`deckit-shell/environment`: `PAGE`), and the page asks main what it is (`deckit-shell/shell/page`), a page the shell made, drawn by its name, or a mod's, run by deck's runner with deckit's layer (`deckit-shell/deckit/mod`) and, once the shell is attached (`attach()` of what connect answers), the shell's lifecycle stacked over deckit's (`deckit-shell/shell/mod`). What deck uses of the environment is what `deckit-shell/environment` declares, and no more: `connect` holds the environment to it before anything starts and keeps only the copy `checked` answers, and each stage it makes is held to `STAGE`, so an environment that drifts fails as it starts. What a member answers when called is not copied. Either side binds the shell's channels with the `channels` it is handed, never with Electron's IPC. A page is a token to the shell: it keys what it keeps by the page and hands it back to deckit (`pages`: open one with the surfaces it may open, close one, focus it, whether it is alive, hear it take the keyboard or end), and reads nothing of it. Pages are laid in a window on a stage the environment makes (`pages.stage()`, `deckit-electron/stage`): the shell says which pages are laid, bottom to top, and which are hidden, and the stage adds, lifts, moves and shows Electron's views to get there. It is an Electron view itself, so a page on it is in the window it is placed in. A page's view is the environment's to know (`deckit-electron/environment`), and a page laid on a stage is found by it until it is taken off. Of a host app the shell asks, beyond what the environment gives it, only that the window honours `-webkit-app-region`, where a press drags it; the frame opens its surfaces with `window.open('', name)`, as `pages.open` declares them, which is the environment's to carry. The host app hands the shell its own pages too (`controls.panel.contains(page)`, `showsPanel`), which the shell only compares with its own or hands back to the environment.

What holds state or reads the configuration is made by its concept's `create...()` and handed what it uses, at its package's root: nothing is made by being imported, and nothing reaches a part another root made but through what that root hands it. The host app's configuration is `connect`'s input, and a renderer holds none of it: main answers what a page needs. What holds no state (a model, a pure function, a protocol's channels) is imported as it is. One exception, by name: what mirrors something a process or a page has only one of lives with that thing, as it does. A process and a page each have one IPC, so `deckit-shell/deck/ipc` keeps, one per bundle, the channels heard on it and the questions on their way across, and `deckit-electron/messages` what Electron's IPC hears; `deckit-shell/deck/listener` stands beside them, as do `connect`'s and `attach`'s once (`connected`, `attached`); in a renderer, the kit's parts that follow its one document (what floats over it, the pointer it captures, its lists, its motion and the kit's stylesheet, in `deckit-shell/shell/ui`) and `deckit-shell/deckit/match/ranker.js`'s one worker. A page runs one kit and one ranker.

A concept's sides are named for Electron's processes: `main.js`, which runs only in main, and `renderer.js`, which runs only in a renderer. Any other file is a part of its concept and runs wherever what imports it runs; a concept not split in sides is usually reached by `index.js`. `protocol.js` is how its own sides reach each other and nobody else's, and what its sides share otherwise is `model/`. A folder is a module (its files and `model/`) or a group (folders only, `model/` not among them); a package's root is a group that also holds `package.json`, `main.js` and `renderer.js`.

Each bundle is its entry and what it imports, through and through, bundled by esbuild: `main.js` and `shell-main.js` (CommonJS, for main) from `deckit-electron/main.js` and `deckit-shell/main.js`, `renderer.js` and `shell-renderer.js` (one global each, for a page's preload) from `deckit-electron/renderer.js` and `deckit-shell/renderer.js`. A package's bundle carries its own copy of what it imports of another. `deckit check`, which the build runs first, holds every file of deckit-electron and deckit-shell to the rules above: every file a script, a package depending only on those it may (deckit-shell on none, deckit-electron on deckit-shell alone, so the shell knows no environment), deckit-shell free of Electron (nothing required, nothing its bundles carry requiring Electron, no `process`, `globalThis`, `eval`, `module` or `Function(`, and no Electron object's name or member in its code, read with its strings and comments left out but what a template puts in, nor one read in brackets or destructured; `View` and `screen`, a page's words too, only in what its main bundle carries), all an environment's bundles carry of the shell plain declarations and pure functions (nothing required, nothing of a process or a page, no state: no binding assigned again, nor one made by a call, `new` or a literal but what `Object.freeze` makes), only the entries of a package its `package.json` depends on, every folder's import inside or beside it and never above, no package of npm imported or required, no `Deckit` global reached, Electron's IPC reached only by `deckit-electron/messages`, no channel named outside its concept and every channel its package's, written out as text and declared once, no cycle, what each bundle carries running where the bundle runs (`main.js` only in main, `renderer.js` only in a renderer, Node only in main), every file in a bundle, every folder a module or a group. Deckit.app and the mods are held only to the built bundles and the runtime contract: the build bundles each mod from its own `src/`.

## 7. One design system

The kit is the shell's, and the one way things look and behave in every page it draws (UI.md):

- One token, derived from the host app's theme and the person's fonts: colours, type, radius, shadow, motion, and a code palette. The kit's stylesheet and every mod read it.
- One stylesheet: hover, press, focus and selection are the platform's states, drawn by rules.
- One overlay: what floats (a menu, a popover, a modal, a drag) is one stack that owns its order, the press outside, Escape and placement.
- One list: rows drawn by key, so what the pointer rests on and what has the focus stay put; one listbox for a list with a cursor, and one tree for the keys of a list or a tree whose items the person selects.
- One shape for each kind of part: a maker takes one options object and returns `{ element, ...its controls }`, a decorator takes an element and returns its dispose, and a control draws the value it is set to and reports what was asked.

## 8. Data

- A rename renames everything, stored keys and channels included. A record's shape is its owner's, and nothing reads an old shape: data written in one is the consumer's to write again.
- A file of a mod's data edited by hand is read at the next start.
