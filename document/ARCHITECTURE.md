# How deckit is built

Deckit is a library a host app embeds to take mods. A mod is what a person adds to the host app, as to a game: a view, a command, a few keys, a way to open an address, a library for other mods, more for another mod to do, a new look, or work done in the app's main process, in any mix.

Deckit is three layers, each built on the one under it:

| Layer | What it is | As an operating system has it |
|---|---|---|
| deck | the engine: what a mod is, running each in a sandbox of its own, what mods give each other (requires and exports, extension points, events), their storage and settings, and the permissions a person grants | the kernel |
| deckit | the platform on deck: the web, windows, keys, commands, opening addresses, the clipboard, notifications and main process modules, and `connect`, which a host app starts it with | the operating system: what an application runs on, on this machine |
| the shell | the surface a person uses deckit through. Deckit's own shell is the panel, which lists the mods with a view and lends the one in front room beside and under its list, the quick switcher, the kit they draw with, and styles; a host app may put its own on deckit instead | the system's interface, as macOS has its menu bar, its Dock and the windows apps draw in |

A mod is an application. The host app is the machine: the process and its windows. It starts deckit, puts a shell on it, and says where the shell is shown. Deck knows nothing of a screen: to deck a mod's page is where the mod runs. Deckit knows no shell: the shell is built on what `connect` answers, as a host app's own would be. A mod runs whether or not the panel is shown.

This document is why deckit is split the way it is, and the rules that keep it so. The contract a mod is written against is [MOD.md](MOD.md); how a host app embeds deckit is [EMBEDDING.md](EMBEDDING.md); the kit mods draw with is [UI.md](UI.md).

## 1. Principles

1. Deckit is whole by itself. `source/deckit` and the documents it ships (EMBEDDING, MOD, UI) are all of it, and name nothing outside it. The package around it is for convenience: its commands check, build, run and ship deckit, with whatever tools serve.
2. A mod can do what the host app can. Permissions say what a mod reaches, and the person agrees to them; none is a dead end, and a main process module has the app's full power. A mod draws its view as it likes; the kit is the quick way, not the only one.
3. Deckit owns only what it makes. The process, its menus and its windows are the host app's; deckit is handed what it needs through `connect()`: its answers and its configuration.
4. A check happens once, where trust changes: main receiving from a page, deck receiving from a mod's code, input from the disk or the network. Inside, each step trusts what the step before it made.
5. A fact has one owner. Everyone else asks it.
6. A layer adds to the one under it and is not known by it: what it gives a mod, what a mod registers with it, the permissions that grant it and the manifest fields it reads, it adds there.
7. A folder is a module or a group, and its dependencies show in where it lies: it uses the folders inside it and beside it, never the one that holds it. A name is the standard term of its field, one name for one act: to reveal is to make something visible where it lies (a file in Finder, an entry in a tree), to show is to bring a view to the front.
8. The packages' names (deckit, deckit-electron, deckit-shell) are the code's; deckit is deck and deckit in Swift, deckit-electron is deck and deckit in Electron, the environment they run in there, and the shell is the layer deckit-shell is, which declares what an environment gives deck and what it and an environment agree on. Deckit is also the product's name, and what goes outside keeps it: the scheme `deckit://`, the `[deckit]` tag, the archive, the default id, and the `deckit.*` permissions, which reach inside the app as `system.*` ones reach past it.

## 2. The packages

```

source/deckit/deckit-electron  deck and deckit in Electron, deck's part that needs Electron in deck/ (the sandbox, the log's file), what deckit does through the system for a mod (environment/: keys caught, opening, notifications, the clipboard, a folder chosen; main-process/, main process modules run; web/, the web pages a mod shows, their sessions, certificates and what a site was allowed), and connect: the environment. Stands on what deckit-shell declares an environment gives it
source/deckit/deckit-shell     deckit's own shell: the panel, the switcher, the kit, styles, and what it and an environment agree on, as plain data: what the shell is given and answers (layer/), text matching (match/), what an environment gives deck (environment/). In deck/, deck's part that needs no environment: how a channel is declared (channel/) and carried (ipc/), which page is whose (identity/), how a listener's throw is reported (listener/), deck's client of the core (core/), deckit's folder and where in it what deckit keeps goes (home/), its copies of the mods (catalog/) and of the state (storage/), the log (log/), what a mod is run by (mod/), the mods' runs (runner/), the mods' records, settings, exports, extension points and events and deck.mods, each a side in main and one on a page, and the mod contract's version (contract/); the shell's other folders and an environment use it, and it uses nothing outside deck/. Beside deck/, deckit's concepts, each its channels, the permissions it checks and what it judges, a side in main and one on a page: the key map (keymap/), commands (command/), opening addresses (open/), notifications (notification/), the clipboard (clipboard/), mod folders (mod-folder/), what runs deckit and restarting it (runtime/), which mod starts its main process modules (main-process/), and the web pages a mod shows, what loads in them and what a site is asked (web/); and which deckit this is (build/). Knows no environment
source/deckit/deckit-app       Deckit.app: deckit embedded by itself, its own host answers framing every window
source/deckit/mods             deckit's own mods, Settings among them, each a mod folder of its own
```

Each is a package of its own. One reaches another only through what that one hands out: its entries, or what it answers at run time.

The package around deckit, `manifest.toml` and `source/cli`, is the commands that check, build, run and ship it (README.md). Deckit names none of it.

A new mod needs no change to deck. A new place to show the panel in needs no change to deckit, and a shell of the host app's own needs no change to deckit.

## 3. Processes and pages

| Where | What runs there |
|---|---|
| the core | deckit's own process, the host app's child: the mods it reads and installs, which of them run and where each run is, what they store, and the state |
| main | deck: the mods, their runs and the state as the core gave them, the pages the mods run in, and what a page asks of deck. Deckit: main process modules, the keymap, opening addresses, commands, windows. The shell: the panel and the switcher, the views it puts in the host app's windows |
| a mod's sandbox | where one mod's entry runs, headless or not: a page in a `WebContentsView` of its own at `deckit://<id>.mod/`; with deckit's shell on deckit, a mod with a view lays it there where the panel's frame leaves it room, or in a region where it is another's child |
| a page that runs no mod | made for the shell, at `deckit://<name>/`: the quick switcher's list, at `deckit://switcher/`, and the panel's frame, at `deckit://panel/`, with the two documents it opens and draws in, its backdrop under the mods and its width's handle over them |

A mod's sandbox is a renderer and deck is in main. Each mod's sandbox has its own origin, its own sessions and its own storage, so one mod cannot reach another's page, data, cookies or what it was allowed; a mod with `deckit.styles` styles another's page, and that is all. Main knows which mod is asking by the page that asks (`deckit-shell/deck/identity`): no page says who it is. A mod's page is held to its origin; a link out of it is offered to its scheme's handlers.

The pages never speak to each other. Main carries everything between them, and every word is a channel declared once in its concept's `protocol.js`, named for its package (`deckit-electron:`, `deckit-shell:`), as `deckit-shell/deck/channel` declares one: `pageToMain` for what a page asks or tells main, `mainToPage` for what main tells or asks a page. A declaration is plain data. `deckit-shell/deck/ipc` binds it, a side each (`main.js`, `renderer.js`), and every channel crosses as a message carrying its channel's name (`deck/ipc/model/envelope.js`), which the environment carries: `deckit-shell/environment` says what an environment gives deck, and Electron carries the messages over the few channels of its IPC in `deckit-electron/messages/protocol.js`, so Electron's IPC knows only those. A question main asks a page and the page's answer go as tells, told apart by the id they carry. A page is a token deck keeps and hands back and never reads; in Electron it is the page's webContents. Binding reads a declaration once and keeps it, so a channel is declared once: binding the same declaration again binds the same channel, and another declaration of its name is refused. A channel is heard once something answers or listens on it, and is answered once. Deck's concepts bind their own as their modules are imported, with `ownChannels`; the shell binds its own with the `channels` it is handed (`layerChannels`), as it is attached and as a page starts it, never under a name deck binds as its own. What carries the channels is handed to each side once, before anything crosses: in main as `connect` starts, on a page as it boots. A question main asks a page is heard from the page's start and waits there for the page's code to say how to answer it, for as long as main waits. A page asking what main does not answer, sync or not, gets an error back, and what a page tells that nothing in main listens on is logged as refused. What main tells a page before the page listens is not kept: a page reads what is so as it starts, and what main told before would come after that. Main holds what arrives to the channel's fields; nothing else checks it. A question main asks a page ends when it is answered, when the page goes away, or when its time runs out. An error crosses with its kind.

The core is `source/deckit/deckit`, a Swift package: `Deck` and `Deckit` on `Deck`, two libraries, and `DeckitServer`, the executable `deckit`, which answers through `Deckit`. It reads the mods and installs them, judges a mod's settings against what its run declared, judges what mods reach of each other, keeps the keymap, and keeps a mod's records, the values of its settings and its data folder, and the state: main asks for a mod's as its page does, and the core answers by the mod main names. A manifest is read against the mod contract main runs mods with and the permissions the layers on deck defined, which main hands the core as it starts, and with the fields deckit adds (`Deckit`). Main reads the mods once the core has installed what the app ships, and again after what changes them, installing, removing or arranging, which only main asks for; what asks at once is answered from that copy. Main reads the state once, before anything on deckit reads it, and answers each read from that copy at once. Main writes the state but for the mods' order and the mods removed with their data still to erase, which the core keeps itself, and the core keeps writes in the order sent, so a write goes to the copy and to the core; one the core refuses is taken back out of the copy. `Deck` and `Deckit` are libraries a Swift host uses as they are, taking and answering Swift's own types: deck's parts (`records`, `settings`, `catalog`, `dataFolder`, `erasure`, `exports`, `extensions`, `events`, `state`), deckit's (`keymap`, `commands`, `urlRouter`), and `Deck` itself for what reads the catalog again and what moves the runs. What is on the wire is the server's (`DeckitServer/Server`): each method's name and params, how each answer is written, a refusal's kind, and the name of what a layer tells has changed (`LayerChange`), which deck carries and does not read. A form stays with its type only when a mod writes it (a contribution, a setting's declaration, a key) or the disk keeps it (a setting's value, a chord a person gave, how they arranged a scheme's handlers); a form only the driver reads or writes is the server's. The state keys a part keeps itself (the mods' order, the mods to clear, the chords a person gave, the scheme handlers) are reserved, and a write of one is refused.

The core runs the mods (`Deck/Lifecycle`, `Deck/Runner`), and main does what running them takes (`deckit-shell/deck/runner`): it makes a mod's page, knows it as the mod's and sets it up before it loads it, asks its `stop()`, closes it and hears it crash, each through what the environment gives deck of a page (`pages`: `make`, `load`, `close`, `watch`), which tells why a page's process ended, so a crash is told the core with its cause whichever of what watches the page hears it first. The app is held from quitting while a run has not ended (`app.onQuit`). Main tells the core what happened, a page that loaded, a run that started, did not start, crashed or stopped, a problem against a run, the mods read again, a relaunch or a quit asked for, and the core answers what follows from it as effects, in order: a run's transition to keep and tell (`tell`), a problem kept (`keep`), a page to make (`open`) or load (`load`), a `stop()` to ask (`stop`), a sandbox going (`closing`) or to close (`close`), and the app free to quit (`quit`). What comes of an effect, a `stop()` answered or timed out, comes back as what happened next, so the core never waits on main. The mods that run are those of the catalog as main last read it, so what runs and main's copy are one. Main keeps each run as the core last told it, one object for as long as the run lasts, with what it contributed (`summary`, `contributions`), which its page reported as it started and the core keeps.

What mods reach of each other, the core judges (`Deck/Export`, `Deck/ExtensionPoint`, `Deck/Event`), and main carries (`deckit-shell/deck/export`, `deckit-shell/deck/extension`, `deckit-shell/deck/event`): main asks whether a call into what a mod exports or extends a point with goes, and which mods hear an event, and sends what the call or the event carries from page to page itself, so it crosses by structured clone and never through the core. What a run exports and extends points with the core keeps and does not read, as JSON text, so its values are copied as JSON. What the core cannot decide yet, a call to a mod that has not started, it answers pending on that mod's run (`{ pending: { mod, run, state } }`), and main asks again once its copy of that run has moved; otherwise it answers `{ ready }`. What changes as runs move comes after a runner's answer's effects: what an optional dependency exports to a mod now (`optionalChanged`), what extends one of a mod's points now (`extensionsChanged`), and the points a mod extends now (`extendsChanged`), which main keeps for the mods' list.

Deckit in the core adds two layers to deck (`Layer`), the keymap's and the URL router's: each reads what a run contributed under its own keys and says what is wrong with it as the run starts, which is recorded against the run, and the keymap adds what of it has changed to a runner's answer. What a run contributes is read only from its launch until it has ended (`Deck.contributions(of:)`). The keymap is deckit's in the core (`Deckit/Keymap`): the keys the host app and its shell register, those each run contributes (`keys`, taken while it runs and as it terminates), the chords the person gave them, kept in the order given, and how a keystroke is resolved against them, each binding with its chord, its issues and the keystroke it answers to. Main keeps the keymap as the core last told it, after a runner's answer (`bindingsChanged`) or as the answer to a change it asked for, whichever came later by its `revision`, and resolves a keystroke against that copy where it lands, as the environment asks whether to take a key at once (`keys.capture`, `deckit-shell/keymap/main.js`). What a key typed to be bound comes to, the core says too. A run contributes by name what it registered for a person to run (`commands`, `now`, `resolve`) and whether it answers addresses (`handleURL`): the core answers which mods offer what (`Deckit/Command`), and where an address goes (`Deckit/Open`), which says too when a mod names schemes and answers none, or the other way. What a scheme is, and which are no place to open, is the core's alone.

Main starts the core once the app is ready, from the file the host app hands `connect` as `core`, which the environment runs (`core.open`, in Electron `deckit-electron/core`), and asks nothing else of it until it has answered `initialize` with deckit's folder, the app's name, the mods it asks first to open each scheme's addresses, the mod contract, the folders of the mods the app ships and of those read in place, and the permissions the layers defined. They speak JSON-RPC 2.0, a message a line: main's requests on the core's stdin and its answers on its stdout, and what it writes to stderr is deckit's log. The core answers one message at a time in the order they come, and asks main nothing. A refusal crosses with its kind, as between main and a page. How the messages go is `deckit-electron/core/connection.js` and `DeckitServer/Connection`; what they are, `deckit-shell/deck/core/message.js` and `DeckitServer/Server`. Deck's client of the core is `deckit-shell/deck/core/main.js`.

A core that ends is not started again. Main logs why, and refuses all that is asked of it after, saying the app is to be restarted, so whatever asked shows it: a mod's write that did not land, on its row in Settings. The core ends as its stdin does, when the host app's process ends, however that ends.

What a mod is, the core says (`Deck/Mod`): its manifest, its folder, its permissions and its entry. `deckit-shell/deck/mod` holds what main runs mods by: the names of the lifecycle's notifications, what an entry exports, the permissions deck checks, and how a name of a mod's is scoped; `deckit-electron/deck/mod` the files of a mod's folder its page is served. They name nothing of running them. Some rules are in both, each where it is used, until what uses the JS one moves to the core: how a name of a mod's is scoped (the core's points and events, and a mod's page), what is inside a mod's folder (the core's entry, main's serving of files) and the names of the lifecycle's notifications (the core's effects, and what main hands the layers on deck before the core has started). Main's runner tells each transition of a run as the core told it (`willLaunch`, `didLaunch`, `didFailToLaunch`, `willTerminate`, `didTerminate`); what follows a mod's run above deck in main (its main process modules, its styles and its place in the panel) listens to those, or asks the run, and changes none of it but to record a problem. The core takes a run's settings only while that run launches.

Deckit's folder is the `home` of the host app's `folders`, or `~/.config/<id>`:

```
mods/           installed mods, a folder each, named by id
data/<id>/      a mod's own files (a main process module's notes, its workspaces)
records/<id>/   a mod's records, one JSON file a key
settings/<id>.json
state/          what the person arranged, and what deck and deckit keep between runs, one JSON file a key
state/host/     what the host app and its shell keep, one JSON file a key
logs/
```

Everything deckit keeps is named from its configured id, so two host apps that embed deckit keep their data apart.

## 5. What a mod is handed

A mod reaches deckit only through `deck`, what its `start` is handed (MOD.md). Before a mod runs, the page's preload puts deckit together, as the host app does in main: the environment's `boot` takes away every global the bundles added and answers what Electron gives the page, and the shell's `start` (`deckit-shell/renderer.js`) runs deckit on the page with it; the mod's entry runs with only `module` and `exports` in reach, as the environment evaluates it.

`deck` is put together by the layers, each adding to it. Deck gives a mod its id and name, its settings and storage, what it requires and uses optionally, `exports` and `caller()`, `extend` and `extensionPoint`, events, and with their permissions `mods` and `modSettings`. Deckit adds the web, opening addresses, the clipboard, notifications, keys, commands and main process modules, and on `mods` picking and revealing mod folders and restarting, and reads the entry's `icon` and `keywords`. The shell on deckit adds the theme, the kit, `show()`, `region()` and `children`, the registrations `view` and `styles`, and on `mods` the panel's pins. A layer's registrations are kinds deck does not know, and what a layer says of a mod (its summary and contributions) deck carries to main and does not read. What a layer gives a mod is never replaced by what a layer above it gives.

Between mods there are two ways, and one question picks: could the host app do this if the other mod were not there?

- If it could not, it is a dependency. A mod names another in `requires` and calls what that one `exports`, through main. A dependency nobody wrote down cannot exist. A mod that runs without the other but does more with it names it in `optional`, an optional dependency: it neither waits for that one nor ends or launches again with it, and is told each time what that one exports to it changes. The other way round, a mod opens an extension point and one that requires it, or has it as an optional dependency, extends the point: what extends it stays in the extending mod's page, and the point's mod calls it through main, never naming it.
- If it could, it is a URL scheme handler. A mod asks for an address to be opened (`deck.open(url)`) without knowing who answers. The mods whose manifest names the scheme are its handlers and are asked in the order the person set, ahead of deckit's own answer, which is always last.

Apart from both, a mod says what happened to it through deck's events (`deckit-shell/deck/event`, judged by the core's `Deck/Event`): `deck.emit(name)` is heard as `<its id>:<name>` by any mod that listens, and no mod speaks for another. Listening takes no dependency. A page's own listeners by name are `deckit-shell/deck/event/bus.js`.

A mod changes how another's pages look with styles, which the shell puts last on each page they style, and nothing else of another mod.

What reaches past a mod's own sandbox (the clipboard, notifications, any web address, another mod's settings, the keymap, other mods' looks, a main process module) is asked for by name in `permissions`, with a reason the person reads when installing. Deck keeps what was granted; each permission is defined by the layer that adds what it grants, before the core starts, and checked there, where the mod asks, by the page it asks from. Deck's own are the core's, and so is `system.global-keys`, which the core's keymap checks. A permission no layer on deck defines is refused.

## 6. Modules

Deckit-electron and deckit-shell are each a package, and every file in them an ES module: it imports what it uses and exports what it is. Inside a package, each folder is one of its concepts, a module: it uses its own folders and the ones beside it, with what they hold, and never the folder that holds it or anything above. A package uses the public surface of the packages it depends on, its entries, from any of its files, and nothing else of them. A package says in its `package.json` what it depends on and its entries (`exports`). Its root holds that file and the two that put it together, `main.js` and `renderer.js`, where it has them; everything else is a concept folder:

| Package | Its entries | What it depends on |
|---|---|---|
| `deckit-electron/` | `main.js`, `connect()` and `SCHEME`; `renderer.js`, `boot()`, the start of a page's preload, which answers what Electron gives the page; `deck/contract/`, the version of the mod contract and the scheme, read with nothing of Electron's (the build reads them for `deckit.json`) | deckit-shell |
| `deckit-shell/` | `main.js`, `attach()`; `renderer.js`, `start()`, deckit on a page; and what it and an environment agree on: `deck/channel/`, how a channel between main and a page is declared, as plain data, and what main holds a page's payload to; `environment/`, what an environment gives deck, on main and on a page, with `checked`; `layer/`, what a layer on deckit is given of what connect answers (`CONNECTED`), and of a stage (`STAGE`), the notifications it hears by name (`NOTIFIED`), and `checked`, which holds a given object to one of these and answers a frozen copy of only what it declares, a member of the wrong kind counting as missing; `match/match.js`, how text is matched, so that what a mod's `deck.util.match` ranks and what the shell's switcher ranks rank alike, and `match/ranker.js`, a mod's `deck.util.ranker` | nothing |

Deckit-shell's `deck/` is a group: deck's part, its concepts the folders in it, which use nothing outside it, so deck names nothing of deckit there. Deckit's concepts lie beside it and use what is in it; `deck/core/`, how main reaches the core, carries deck's configuration and deckit's in `initialize`. Deckit-electron's `deck/` holds what of deck needs Electron (the sandbox, the log's file, the scheme), and its root puts the environment, deck's parts and deckit's together, making the environment first and deck's parts before deckit's.

In main the shell reaches deckit through what connect answers, handed to `attach` (`deckit-electron/api/`). On a page deckit is the shell's: the preload hands `start` what `boot` answers the environment gives a page (`deckit-shell/environment`: `PAGE`), and the page asks main what it is (`deckit-shell/page`), a page the shell made, drawn by its name, or a mod's, run by deck's runner with deckit's layer of `deck` and, once the shell is attached (`attach()` of what connect answers), the shell's over it (`deckit-shell/mod`). What the shell uses in main, and of a stage, is what `deckit-shell/layer` declares, and no more: `connect` holds its answer to it before anything starts, and `attach` and the stages it makes keep only the copy `checked` answers, so an environment that drifts fails as it starts and the shell reaches nothing it is not given. What a member answers when called is not copied: a run from `mods.runs()` carries more than the shell reads. Either side binds the shell's channels with the `channels` it is handed, never with Electron's IPC. A page is a token to the shell: it keys what it keeps by the page and hands it back to deckit (`pages`: open one with the surfaces it may open, close one, focus it, whether it is alive, hear it take the keyboard or end), and reads nothing of it. Pages are laid in a window on a stage the environment makes (`pages.stage()`, `deckit-electron/stage`): the shell says which pages are laid, bottom to top, and which are hidden, and the stage adds, lifts, moves and shows Electron's views to get there. It is an Electron view itself, so a page on it is in the window it is placed in. A page's view is the environment's to know (`deckit-electron/page`, a mod's from `deckit-electron/environment`), and a page laid on a stage is found by it until it is taken off. Of a host app the shell asks, beyond what the environment gives it, only that the window honours `-webkit-app-region`, where a press drags it; the frame opens its surfaces with `window.open('', name)`, as `pages.open` declares them, which is the environment's to carry. The host app hands the shell its own pages too (`controls.*.contains(webContents)`, `showsPanel`, `summonSwitcher`), which the shell only compares with its own or hands back to the environment.

What holds state or reads the configuration is made by its concept's `create...()` and handed what it uses, at its package's root: nothing is made by being imported, and nothing reaches a part another root made but through what that root hands it. The host app's configuration is `connect`'s input, and a renderer holds none of it: main answers what a page needs. What holds no state (a model, a pure function, a protocol's channels) is imported as it is. One exception, by name: what mirrors something a process or a page has only one of lives with that thing, as it does. A process and a page each have one IPC, so `deckit-shell/deck/ipc` keeps, one per bundle, the channels heard on it and the questions on their way across, and `deckit-electron/messages` what Electron's IPC hears; `deckit-shell/deck/listener` stands beside them, as do `connect`'s and `attach`'s once (`connected`, `attached`); in a renderer, the kit's parts that follow its one document (what floats over it, the pointer it captures, its lists, its motion and the kit's stylesheet, in `deckit-shell/ui`) and `deckit-shell/match/ranker.js`'s one worker. A page runs one kit and one ranker.

A concept's sides are named for Electron's processes: `main.js`, which runs only in main, and `renderer.js`, which runs only in a renderer. Any other file is a part of its concept and runs wherever what imports it runs; a concept not split in sides is usually reached by `index.js`. `protocol.js` is how its own sides reach each other and nobody else's, and what its sides share otherwise is `model/`. A folder is a module (its files and `model/`) or a group (folders only, `model/` not among them); a package's root is a group that also holds `package.json`, `main.js` and `renderer.js`.

Each bundle is its entry and what it imports, through and through, bundled by esbuild: `main.js` and `shell-main.js` (CommonJS, for main) from `deckit-electron/main.js` and `deckit-shell/main.js`, `renderer.js` and `shell-renderer.js` (one global each, for a page's preload) from `deckit-electron/renderer.js` and `deckit-shell/renderer.js`. A package's bundle carries its own copy of what it imports of another. `deckit check`, which the build runs first, holds every file of deckit-electron and deckit-shell to the rules above: every file a script, a package depending only on those it may (deckit-shell on none, deckit-electron on deckit-shell alone, so the shell knows no environment), deckit-shell free of Electron (nothing required, nothing its bundles carry requiring Electron, no `process`, `globalThis`, `eval`, `module` or `Function(`, and no Electron object's name or member in its code, read with its strings and comments left out but what a template puts in, nor one read in brackets or destructured; `View` and `screen`, a page's words too, only in what its main bundle carries), what of the shell an environment's bundle and the shell's carry in one place, and all an environment's page bundle carries of it, plain declarations and pure functions (nothing required, nothing of a process or a page, no state: no binding assigned again, nor one made by a call, `new` or a literal but what `Object.freeze` makes), only the entries of a package its `package.json` depends on, every folder's import inside or beside it and never above, no package of npm imported or required, no `Deckit` global reached, Electron's IPC reached only by `deckit-electron/messages`, no channel named outside its concept and every channel its package's, written out as text and declared once, no cycle, what each bundle carries running where the bundle runs (`main.js` only in main, `renderer.js` only in a renderer, Node only in main), every file in a bundle, every folder a module or a group. Deckit.app and the mods are held only to the built bundles and the runtime contract: the build bundles each mod from its own `src/`.

## 7. One design system

The kit is the shell's, and the one way things look and behave in every page it draws (UI.md):

- One token, derived from the host app's theme: colours, type, radius, shadow, motion, and a code palette. The kit's stylesheet and every mod read it.
- One stylesheet: hover, press, focus and selection are the platform's states, drawn by rules.
- One overlay: what floats (a menu, a popover, a modal, a drag) is one stack that owns its order, the press outside, Escape and placement.
- One list: rows drawn by key, so what the pointer rests on and what has the focus stay put; one listbox for a list with a cursor, and one tree for the keys of a list or a tree whose items the person selects.
- One shape for each kind of part: a maker takes one options object and returns `{ element, ...its controls }`, a decorator takes an element and returns its dispose, and a control draws the value it is set to and reports what was asked.

## 8. Data

- A rename renames everything, stored keys and channels included. A record's shape is its owner's, and nothing reads an old shape: data written in one is the consumer's to write again.
- A file of a mod's data edited by hand is read at the next start.
