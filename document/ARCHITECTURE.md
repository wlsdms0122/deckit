# How deckit is built

Deckit is a library a host app embeds to run mods. A mod is what a person adds to the host app: a window or a view, keys, what it declares to other mods' interfaces, exports for the mods that use it, a new look for other mods' pages, or work done in the app's main process, in any mix.

Deckit is built in layers, each on the one under it:

| Layer | Where | What it is |
|---|---|---|
| the environment, the driver | `source/deckit/deckit-electron`, with the web engine addon `source/deckit/deckit-web` | what deck and deckit run on in Electron: the pages deckit makes and what they tell, every page on WebKit through deckit-web's module, messages between main and a page, the core's process, the windows the host app opens, a stage to lay pages on, platform notifications, the clipboard, a person's files, the web pages a mod shows, and a mod's main process modules. It gives what `deckit-shell/environment` declares an environment gives |
| Deck, the kernel | the Swift library `Deck`, in the core, `source/deckit/deckit` | principals and the jobs they run, each run in a sandbox of its own, its lifecycle, and the effects the driver does with what it decided; each principal's storage (its records, its data folder and what a layer above keeps for it) and erasing it; the owner of each interface; connections and events between runs. It knows no mod: a principal is a name, and what a job contributes it carries without reading |
| Deckit, the system services and policy | `source/deckit/deckit-shell/deckit`, and its side in the core, the Swift library `Deckit` | in the core, what a mod is and the policy over mods: the manifest, installing, the catalog and its order, the system mods and the privileged permissions only they are granted, which mods launch and when (the background mods at start, the relaunch limit, a run's time), the state, and deckit's own permissions. In main and on a mod's page, the passage to the core: what a mod's page is handed (`deckit`) and what carries each call, the runner and the lifecycles stacked on a run, connections, events, records, `deckit.mods`, and the platform services a mod reaches: notifications, the clipboard, opening outside the app, and what runs deckit. `connect` starts it on an environment |
| the system mods, the services | `source/deckit/mods` | mods the host app ships and names system mods, each run as any mod is, with the privileged permissions only a system mod is granted. Commands (`mods/commands`, `deckit/commands`), keys (`mods/keymap`, `deckit/keys`), configuration (`mods/configuration`, `deckit/configuration`), opening addresses (`mods/urls`, `deckit/urls`) and notifications (`mods/notifications`, `deckit/notifications`) are each the interface a system mod provides |
| the Deckit Shell, the desktop | `source/deckit/deckit-shell/shell` | the desktop in the host window: its own page, `deckit://desktop/`, with the backdrop, the frames of the mods' normal windows and the Dock; the windows mods open, normal on the desktop or overlay in a floating window of the host app's; the overlay over each page it draws in; the regions a mod gives other mods' views; the keys of the app, in one table of chords; styles, the theme and the fonts. It is attached on what `connect` answers (`attach`) and stacks the screen lifecycle (`attach`, `detach`) on a mod's run, with the handle `shell`. Deckit runs its mods whether or not a host app attaches it |
| the distribution | `source/deckit/deckit-app` | Deckit.app: deckit embedded by itself, its own host answers framing every window, and the mods it ships, each a system mod |
| the SDK | `source/deckit/deckit-sdk` | the libraries a mod bundles (`match`, `path`), and the page frameworks a page's preload loads and hands a mod (`deckit/`, `shell/`, `web/`), with their headers |

Beside the shell, the web engine (`source/deckit/deckit-shell/web`) is a layer over deckit with no lifecycle of its own: a mod's web sessions and the web pages it shows. A mod's main process modules (`deckit-electron/main-process`) are such a layer too.

A mod is an application. The host app is the machine: the process and its windows. It makes the environment, starts deckit on it with `connect`, attaches the web engine and the shell, and says where the desktop is shown. Deck knows no mod and no screen: to deck a mod is a principal, and its page is where its job runs. Deckit knows no shell: the shell is built on what `connect` answers, as a host app's own would be. A mod runs whether or not a shell draws it: what it does is registered in deckit's lifecycle, and what it shows in the shell's, stacked over it (MOD.md, Lifecycles). A lower layer holds only the questions its own mechanism asks, and the layer above answers them.

This document is why deckit is split the way it is, and the rules that keep it so. The contract a mod is written against is [MOD.md](MOD.md); how a host app embeds deckit is [EMBEDDING.md](EMBEDDING.md); the kit mods draw with is [UI.md](UI.md).

## 1. Principles

1. Deckit is whole by itself. `source/deckit` and the documents it ships (EMBEDDING, MOD, UI) are all of it, and name nothing outside it. The package around it is for convenience: its commands check, build, run and ship deckit, with whatever tools serve.
2. A mod can do what the host app can. Permissions say what a mod reaches, and the person agrees to them; none is a dead end, and a main process module has the app's full power. A mod draws its view as it likes; the kit is the quick way, not the only one.
3. Deckit owns only what it makes. The process, its menus and its windows are the host app's; deckit is handed what it needs through `connect()`: the environment, the app's answers and its configuration.
4. A check happens once, where trust changes: main receiving from a page, the core receiving from a mod's code, input from the disk or the network. Inside, each step trusts what the step before it made.
5. A fact has one owner. Everyone else asks it.
6. A layer adds to the one under it and is not known by it: what it gives a mod, what a mod registers with it, the permissions that grant it and the manifest fields it reads, it adds there.
7. A folder is a module or a group, named for its concept. Folders beside each other use each other one way, never back, directly or through others; what is in a folder uses what the folder may, and never the folder that holds it. A name is the standard term of its field, one name for one act: to reveal is to make something visible where it lies (a file in its folder, an entry in a tree), to show is to bring a view to the front.
8. The packages' names (deckit, deckit-electron, deckit-shell, deckit-sdk) are the code's: deckit is the core, the Swift libraries `Deck` and `Deckit` and the server on them; deckit-electron is the environment in Electron; deckit-shell is Deckit's services, the web engine's and the shell's, and declares what an environment gives them; deckit-sdk is the SDK. Deckit's platform services are defined in deckit-shell and deckit-sdk (`deckit/`) and implemented by the environment. Deckit is also the product's name, and what goes outside keeps it: the scheme `deckit://`, the `[deckit]` tag, the archive, the default id, and the `deckit.*` permissions, which reach inside the app as `system.*` ones reach past it.

Each is a package of its own. One reaches another only through what that one hands out: its entries, or what it answers at run time.

The package around deckit, `manifest.toml` and `source/cli`, is the commands that check, build, run and ship it (README.md). Deckit names none of it.

A new mod needs no change to deck or deckit, and a shell of the host app's own needs no change to deckit.

## 3. Processes and pages

| Where | What runs there |
|---|---|
| the core | deckit's own process, the host app's child: the mods it reads and installs, which of them run and where each run is, what they store, and the state |
| main | Deckit's services: the mods, their runs and the state as the core gave them, the pages the mods run in, and what a page asks of deckit. The main process modules: a mod's modules run in main. The web engine: the web pages mods show. The shell: the desktop, the mods' windows and the keys of the app |
| a mod's sandbox | where one mod's entry runs, headless or not: a page of WebKit's of its own at `deckit://<id>.mod/`, its code run in WebKit's own processes; with the shell attached, a mod's window shows what the page opened for it, and a mod's view is shown in a region of another mod's window where it is that mod's child |
| a web page a mod shows | WebKit: a view in main's process, laid just over the mod's page where the page's element is and cut to the page, over what the page draws and under the page's overlay, its site run in WebKit's own processes, and its session a data store of WebKit's of its own |
| a page that runs no mod | made for the shell, at `deckit://<name>/`: the desktop's page, at `deckit://desktop/`, where the backdrop, the windows' frames and the Dock are drawn |
| a page's overlay | a document each page the shell draws in opens beside itself, `about:blank` named `deckit-overlay`, where the kit draws the page's layers; laid at the page's rect over all that is laid with it while it shows anything, taking the pointer where it draws what takes it |

A mod's sandbox is a page and the core's client is in main. Each mod's sandbox has its own origin, its own sessions and its own storage, so one mod cannot reach another's page, data, cookies or what it was allowed; a mod with `deckit.styles` styles another's page, and that is all. Main knows which mod is asking by the page that asks (`deckit-shell/deckit/identity`): no page says who it is. A mod's page is held to its origin: a navigation out of it is refused.

The pages never speak to each other. Main carries everything between them, and every word is a channel declared once in its concept's `protocol.js`, named for the package whose `main.js` answers it at the protocol's path below its package's root (`deckit-electron:`, `deckit-shell:`), as `deckit-sdk/deckit/channel` declares one: `pageToMain` for what a page asks or tells main, `mainToPage` for what main tells or asks a page. A declaration is plain data. `deckit/ipc` binds it, a side each (`main.js` in deckit-shell, `renderer.js` in deckit-sdk), and every channel crosses as a message carrying its channel's name (`deckit/ipc/model/envelope.js`), which the environment carries: `deckit-shell/environment` says what an environment gives deckit, and Electron's carries the messages over WebKit's (`deckit-electron/messages/protocol.js`): a page tells main by posting to its message handler and asks it by a request to its own origin, which a question the page waits on holds the page for, and main tells a page by calling a function deckit's world keeps. A question main asks a page and the page's answer go as tells, told apart by the id they carry. A page is a token deckit keeps and hands back and never reads; in Electron's environment it is the module's page. Binding reads a declaration once and keeps it, so a channel is declared once: binding the same declaration again binds the same channel, and another declaration of its name is refused. A channel is heard once something answers or listens on it, and is answered once. Deckit's concepts bind their own as their modules are imported, with `ownChannels`; the shell binds its own with the `channels` it is handed (`layerChannels`), as it is attached and as a page starts it, never under a name deckit binds as its own. What carries the channels is handed to each side once, before anything crosses: in main as `connect` starts, on a page as it boots. A question main asks a page is heard from the page's start and waits there for the page's code to say how to answer it, for as long as main waits. A page asking what main does not answer, sync or not, gets an error back, and what a page tells that nothing in main listens on is logged as refused. What main tells a page before the page listens is not kept: a page reads what is so as it starts, and what main told before would come after that. Main holds what arrives to the channel's fields; nothing else checks it. A question main asks a page ends when it is answered, when the page goes away, or when its time runs out. An error crosses with its kind.

The core is `source/deckit/deckit`, a Swift package: the libraries `Deck` and `Deckit` on `Deck`, and `DeckitServer`, the executable `deckit`, which answers through `Deckit`. `Deck`'s parts are a principal's `records`, `principalState`, `dataFolder`, `storage` and `erasure`, the `owners` of each interface, `connections` and `events`, and the runner it moves the runs with. `Deckit` adds the mods to it: the `catalog` (`Deckit/Mod`: the manifest, installing, the mods read and their order), the `state` (`Deckit/State`), the `runs` it keeps (`Deckit/Run`: an entry for each run that launches, the relaunch limit and a run's time) and deckit's own permissions. It reads the mods and installs them, judges a manifest against the mod contract main runs mods with, the permissions the layers defined and the fields they add, which main hands the core as it starts, and grants a privileged permission only to a system mod. Main reads the mods once the core has installed what the app ships, and again after what changes them; what asks at once is answered from that copy. Main reads the state once, before anything on deckit reads it, and answers each read from that copy at once; a write goes to the copy and to the core, which keeps writes in the order sent. What is on the wire is the server's (`DeckitServer/Server`): each method's name and params, how each answer is written, and a refusal's kind.

The core decides which mods launch and when (`Deckit`, on `Deck/Run/Runner`): the background mods as the app starts, a mod as something launches it, as a lifecycle reaches it by id, or as a lifecycle waits for the owner of an interface it uses, and a background mod again after its run fails, until the relaunch limit. Main does what running them takes (`deckit-shell/deckit/runner`): it asks the core to start, load, launch, quit and unload mods, unloads them all as the app quits, and makes a mod's page, knows it as the mod's and sets it up before it loads it, asks it to end its lifecycles, closes it and hears it crash, each through what the environment gives deckit of a page (`pages`: `make`, `load`, `close`, `watch`). The app is held from quitting while a run has not ended (`app.onQuit`). Main tells the core what happened, a run that started, did not start, crashed or stopped, a problem against a run, and the core answers what follows from it as effects, in order: a sandbox to make (`open`) or its page to load (`loadPage`), a run's transition to keep and tell (`tell`) or a run kept (`keep`), an end to ask (`stop`), a sandbox to end at once (`kill`) or close (`close`), a connection made or ended (`connect`, `disconnect`), an event to deliver (`deliver`), and a lifecycle told it waits (`wait`) or is refused (`refuse`). What comes of an effect, an end answered or timed out, comes back as what happened next, so the core never waits on main. Main keeps each run as the core last told it, one object for as long as the run lasts, with what it contributed (`summary`, `contributions`), which its page reported as it started and again as each lifecycle above the first joined. The page tells too, once its entry is evaluated, what the layers read of the class (`described`), and how many lifecycles it stacks, so main waits for each to end in its own time.

What mods reach of each other, the core judges (`Deck/Reach/Connection`, `Deck/Reach/Event`), and main carries (`deckit-shell/deckit/connection`, `deckit-shell/deckit/event`): which connections stand and whether a message on one goes, and which mods hear an event. Main sends what a message or an event carries from page to page itself, and never through the core. As a lifecycle of a run begins, its page asks main for its connections (`connection/begin`), and as it ends, it tells main (`connection/end`); a lifecycle that reaches a mod by its id asks for it and lets it go (`connection/reach`, `connection/release`). A message on a connection is judged by one question, whether the connection stands and the page that sends it is one of its ends (`connection/route`), and goes to the other end. A connection whose service's page refused it stays down while both its ends are up (`connection/refuse`).

Main starts the core once the app is ready, from the file the host app hands the environment as `core`, which the environment runs (`core.open`, in Electron `deckit-electron/core`), and asks nothing else of it until it has answered `initialize` with deckit's folder, the mod contract, the mods the app ships, each its folder and whether the host app names it a system mod, the folders of the mods read in place, the permissions the layers defined and the manifest fields they add. The core answers where it keeps the mods and the data folders, and how long a run is given. They speak JSON-RPC 2.0, a message a line: main's requests on the core's stdin and its answers on its stdout, and what it writes to stderr is deckit's log. The core answers one message at a time in the order they come, and asks main nothing. A refusal crosses with its kind, as between main and a page. How the messages go is `deckit-electron/core/connection.js` and `DeckitServer/Transport`; what they are, `deckit-shell/deckit/core/message.js` and `DeckitServer/Server`. Deckit's client of the core is `deckit-shell/deckit/core/main.js`.

A core that ends is not started again. Main logs why, and refuses all that is asked of it after, saying the app is to be restarted, so whatever asked shows it. The core ends as its stdin does, when the host app's process ends, however that ends.

| a mod's web sign-ins | its own sessions, `persist:<id>:<mod>:<name>` |
| what the layers keep between runs | the core, `Deckit/State`, in `state/`, an owner of its own in a folder of its own: the web engine's (the web sessions each mod used, its downloads) in `state/web/`, the shell's (where windows were left, the Dock, the chords given its keys, the fonts) in `state/shell/`, a host app's in a folder it names |

What a mod is, the core says (`Deckit/Mod/Manifest`): its manifest, its folder, its permissions and its entry. `deckit-shell/deckit/runner/model/lifecycle.js`, `deckit-sdk/deckit/permission` and `deckit-shell/deckit/event/model/scoped-name.js` hold what main runs mods by: the names of the lifecycle's notifications, deckit's permission ids, and how a name of a mod's is scoped; `deckit-electron/mod` the files of a mod's folder its page is served. They name nothing of running them. Main's runner tells each transition of a run as the core told it (`willLaunch`, `didLaunch`, `didFailToLaunch`, `willTerminate`, `didTerminate`), and `didJoin` once a lifecycle over the first has joined, or failed and ended, which changes what the run contributes; what follows a mod's run above deckit in main (its main process modules, its styles, its windows and its place in the Dock) listens to those, or asks the run, and changes none of it but to record a problem.

Deckit's folder is the `home` of the host app's `folders`, or `~/.config/<id>`:

```
deck.json       deck's settings: each interface's queue of providers (`providers`), the person's pins (`pins`), and the mods still to erase (`uncleared`)
mods/           installed mods, a folder each, named by id, with the lists of those installed, in the order they were installed (`.installed`), shipped (`.shipped`) and system mods (`.system`)
data/<id>/      a mod's own files (a main process module's notes, its workspaces)
records/<id>/   a mod's records, one JSON file a key
principal-state/<name>/<id>.json   what a layer above deck keeps for a mod, by the name it reserves
state/          what the person arranged, and what the layers keep between runs, one JSON file a key
state/shell/    what deckit's shell keeps, one JSON file a key
state/web/      what the web engine keeps, one JSON file a key
logs/
```

The core lays out all but `logs/`, which is main's, and answers `initialize` with where it keeps the mods and the data folders, and each mod it reads with its own data folder (`data`), which main hands the mod's main process modules.

Everything deckit keeps is named from its configured id, so two host apps that embed deckit keep their data apart.

## 5. What a mod is handed

A mod reaches deckit only through its handles: `deckit`, which `start` and `attach` are handed, and `shell`, which only `attach` is (MOD.md). Before a mod runs, the page's preload puts deckit together, as the host app does in main: the environment's `boot` takes away every global the bundles added and answers what the environment gives the page, and the shell's `start` (`deckit-shell/renderer.js`) runs deckit on the page with it; the mod's entry runs with only `module` and `exports` in reach, as the environment evaluates it.

Deckit's runner evaluates the entry, and each layer reads the class it exports. The runner makes one instance of it and runs the lifecycles the layers on it stack, each layer its own over those of the layers under it, the lowest first, each with handles of its own and a scope that cuts, as it ends, what its handles made that calls back into the mod's code. The runner knows neither how many lifecycles there are nor their names: it joins what each registered as its start ends, tells main the first as the run starting and each after as it joining, ends them the highest first, and fails the run only when the first fails. Each lifecycle is connected to the exports it reaches as it begins, before its method is called, and its connections end once its end method has run and what its handles made is cut. `exports` is registered once for the run for each interface the mod provides, and once for its own, in whichever lifecycle has the job. A layer is handed what the layer under it offers one over it.

The handle `deckit` is the runner's members and deckit's. The runner gives a mod its `id` and `name`, its `storage` (`values`, `records`), `dependencies`, the exports it reaches, `exports`, `events`, `quit()`, and `mods`, whose members a mod without `deckit.mods` is refused. Deckit adds `contributions` on `exports`, what mods declare to an interface the mod owns, `openExternal`, `fileURL` and `filePath`, `about`, the clipboard (`clipboard`), platform notifications (`notifications`), and `restart` on `mods`. The shell on deckit stacks the screen lifecycle and hands it the handle `shell`, every member on it whatever the mod is granted: `view` and `styles`, each with its `register`, which registers styles for a mod granted `deckit.styles`, and `exports`; the theme (`theme`), the kit (`ui`), the mod's windows (`windows`), `region()` and `children`, `dropDestination()`, `web`, the web pages of a session as the web engine's layer offers them, `keys`, the chords the mod takes, and `active()`, whether the app is in front, `dialogs` and `reveal()`, `fonts`, whose `set` `deckit.fonts` guards, and the Dock's `mods`, which `deckit.mods` guards. A guarded request of the handle is refused `NOT_PERMITTED` as deckit's are. The web engine on deckit is a layer with no lifecycle of its own, a framework: it hands every lifecycle the handle `web`, the mod's web sessions and downloads, in the table of frameworks by name after the lifecycle's own arguments (`start(deckit, { web })`, `attach(shell, deckit, { web })`), made for that lifecycle and cut as it ends. The main process modules on deckit are a framework the same way: the handle `mainProcess` starts the mod's modules in the host's own process (`start(deckit, { mainProcess })`). A layer's registrations are kinds the runner does not know, and what a layer says of a mod (its summary and contributions) deckit carries to main and the core does not read. What a layer gives a mod is never replaced by what a layer above it gives: a name a lower lifecycle registered stands, and the higher one's is left out.

Between mods one rule says where a call goes: a caller that names who it calls goes to that mod, by id; one that does not goes by a role. An event and a style name a mod. An interface names its owner, one mod among those that provide it, and the system's services are interfaces: running a command, a key, a configuration, opening an address and posting a notification each go to the owner of its interface.

- A mod names an interface in `uses` and is connected to the exports the interface's owner opens for it. A mod that uses an interface never learns which mod owns it; the owner knows each mod it is connected to, and what each declares to the interface in its `contributes`.
- A mod with `deckit.reach-mods` reaches another by its id, which launches that mod if it does not run, and is connected to the exports that mod opens for its own id.

Apart from both, a mod says what happened to it through events (`deckit-shell/deckit/event`, judged by the core's `Deck/Reach/Event`): `deckit.events.emit(name)` is heard as `<its id>:<name>` by the mods that listen and may hear it, and no mod speaks for another. A page's own listeners by name are `deckit-sdk/deckit/event/bus.js`. An event carries values only: a function crosses only a connection, which has an end at which to let it go.

Deckit has one device between mods' pages, `deckit-shell/deckit/connection`. A connection stands between the exports a mod opened in one lifecycle and one lifecycle of a mod that reaches it, and ends as either ends (MOD.md). It is built in three layers:

| Layer | What it does | What it does not know |
|---|---|---|
| the core, `Deck/Reach/Connection` | stands connections up and ends them, from the manifests' `uses`, the mods a lifecycle reaches by id, the owner of each interface and the lifecycles up on both ends; judges a message by one question, whether the connection stands and the sender is one of its ends; tells both pages as a connection stands and as it ends | what crosses, and how many references there are |
| the wire, `deckit-shell/deckit/connection/protocol.js` and `model/wire.js` | the shape of what crosses: `{ value, references }`, `value` JSON with each function left out, and `references` a `[path, number]` for each. The same shape carries exports, args and results. Three messages: `call` on a number, its answer (what it returns, or `{ name, message, kind }` thrown), and `release` of a number | the language |
| the binding, `deckit-shell/deckit/connection/renderer.js` | moves the language's values to the wire and back. For each connection it keeps a table of the functions it handed over, by number, and of the references it holds, by number, and drops both as the connection ends | the other mod's language |

A number is from the table of the end that handed the function over, and means something only on its connection: the same function handed twice on one connection is one number. Every call is a message, so every call is asynchronous. A reference received is never handed on, so whatever calls into a page is the mod connected to it.

The architecture is the same whatever language a mod's page runs: only the binding is language specific. A binding says which of its language's values are data and which cross as references, how a received reference is called and how it learns the page holds it no more, and how `dependencies[<interface>]` reads in that language. The JavaScript binding copies an object's own enumerable data, sends its functions and its class's methods as references bound to it, makes each number one function answering a promise, and learns of one held no more through a `FinalizationRegistry`.

A mod changes how another's pages look with styles, which the shell puts last on each page they style, and nothing else of another mod.

What reaches past a mod's own sandbox (the clipboard, notifications, any web address, handing a file on, a window over every app, keys in every app, other mods' looks, other mods reached by id, a main process module) is asked for by name in `permissions`, with a reason the person reads when installing. Each layer on this host defines those of what it adds, before the core starts, and checks them where the mod asks, by the page it asks from; the core keeps what each mod asked for. Deckit's own (`deckit.mods`, `deckit.reach-mods`, `deckit.system-services`) are the core's (`Deckit`); a privileged permission is granted only to a system mod. One no layer on this host defines is not usable here (`usable` on the manifest's permission), and the mod runs without what it guards.

## 6. Modules

Deckit-electron, deckit-shell and deckit-sdk are each a package, and every file in them an ES module: it imports what it uses and exports what it is. Inside a package, each folder is one of its concepts, a module or a group of them: folders beside each other use each other one way, never back, directly or through others, what is in a folder uses what the folder may, and nothing uses the folder that holds it. A mod's `src/` and `main-process/` keep the same shape, with only the entry beside the concept folders in `src/`. A package uses the public surface of the packages it depends on, its entries, from any of its files, and nothing else of them. A package says in its `package.json` what it depends on and its entries (`exports`). Its root holds that file and the two that put it together, `main.js` and `renderer.js`, where it has them; everything else is a concept folder:

| Package | Its entries | What it depends on |
|---|---|---|
| `deckit-electron/` | `main.js`, `environment()`, `API` and `attachMainProcess()`, which puts a mod's main process modules on deckit; `renderer.js`, `boot()`, the start of a page's preload, which answers what the environment gives the page, and `LAYERS`, the main process modules' layer; `contract/`, the version of the mod contract, read with nothing of Electron's (the build reads it for `deckit.json`) | deckit-shell, deckit-sdk |
| `deckit-shell/` | `main.js`, `connect()`, `attachWeb()` and `attach()`; `renderer.js`, `start()`, deckit on a page; `environment/`, what an environment gives deckit, on main and on a page (`MAIN`, `PAGE`), what it gives the web engine (`WEB`, `WEB_PAGE`), what the web engine hands the environment's web, its client (`WEB_CLIENT`), what it gives the shell (`SHELL`) and a stage (`STAGE`), with `checked`, which holds a given object to one of these and answers a frozen copy of only what it declares, a member of the wrong kind counting as missing; `deckit/contract/`, the mod contract's version; `web/engine/model/site.js` and `site-permission.js`, a site's origin and the permissions a site is asked for or given | deckit-sdk |
| `deckit-sdk/` | `match` and `path`, the libraries a mod bundles; and to a package that resolves with the condition `os`, every file of `deckit/`, `shell/` and `web/`: the owners' frameworks and their headers | nothing |

Deckit-shell's root holds three groups, each with what an environment gives it (`environment/`), which the root's `environment/` gathers: `deckit/`, Deckit's services; `web/`, the web engine's, which uses nothing of `shell/`; and `shell/`, the shell's. `deckit/core/`, how main reaches the core, carries the permissions and the manifest fields the layers define in `initialize`. Deckit-electron's root makes the environment, and its folders are its parts, each beside the others. `connect` holds the environment to what deckit is given and configures it first.

In main the shell reaches deckit through what connect answers, handed to `attach` (`deckit-shell/deckit/api/`), as a host app's own would be, and the environment through what `attach` holds it to (`SHELL`). The web engine reaches deckit the same way, through what connect answers handed to `attachWeb`, and the environment through `WEB`; the main process modules too, handed to `attachMainProcess`, and the environment through its `mainProcess`. The shell reaches the web engine through what `attachWeb` answered, handed to `attach` as `web`, and on a page through what the web engine's layer offers it; the web engine never reaches the shell. On a page deckit is the shell's: the preload hands `start` what `boot` answers the environment gives a page (`deckit-shell/environment`), and the page asks main what it is (`deckit-shell/deckit/setup`), a page that runs no mod, drawn by its name, or a mod's, run by deckit's runner with deckit's layer (`deckit-sdk/deckit/mod`) and the layers stacked over it, by name: once the main process modules are attached, theirs, which hands every lifecycle the handle `mainProcess` (`deckit-electron/main-process`), the preload handing it to `start`; once the web engine is attached (`stack()` of what connect answers), the web engine's, which hands every lifecycle the handle `web` and offers a layer over it `surfaces`, the web pages of a session (`deckit-shell/web/attach`); once the shell is attached, the shell's, its lifecycle over deckit's (`deckit-sdk/shell/mod`). What deckit uses of the environment is what `deckit-shell/environment` declares, and no more: `connect` holds the environment to it before anything starts and keeps only the copy `checked` answers, `attachWeb` and `attach` hold it to what the web engine and the shell use the same way, and each stage the shell makes is held to `STAGE`, so an environment that drifts fails as it starts. What a member answers when called is not copied. Either side binds the shell's channels with the `channels` it is handed, never with the environment's messages. A page is a token to the shell: it keys what it keeps by the page and hands it back (`deckit-shell/shell/page`), and reads nothing of it. Pages are laid in a window on a stage the environment makes (`deckit-electron/stage`): the shell says which pages are laid, bottom to top, and which are hidden, and the stage lays the module's pages to get there, a hidden page out of the window, and the web pages a page shows just over it. Where a page laid on it marks itself `--app-region: drag`, a press drags the window (`STAGE`), so the shell asks a host app for nothing beyond what the environment gives it. A page opens a window's content and its overlay with `window.open('', name)`, as the shell allows it (`SHELL.pages.surfaces`), which is the environment's to carry. A page's overlay (`deckit-sdk/shell/overlay`) is where the kit draws the page's layers, and whatever lays the page lays it at the page's rect over all it lays while it shows anything, so its layers are over the other pages and the page's web pages; it takes the pointer where a layer draws what takes it. The keyboard is the overlay's while an element drawn in it holds the focus, once pressed there or given the keyboard the page has.

What holds state or reads the configuration is made by its concept's `create...()` and handed what it uses, at its package's root: nothing is made by being imported, and nothing reaches a part another root made but through what that root hands it. The host app's configuration is `connect`'s input, and a renderer holds none of it: main answers what a page needs. What holds no state (a model, a pure function, a protocol's channels) is imported as it is. One exception, by name: what mirrors something a process or a page has only one of lives with that thing, as it does. A process and a page each have one IPC, so `deckit/ipc` keeps, one per bundle, the channels heard on it and the questions on their way across, and `deckit-electron/messages`, on a page, what main tells it and how many posts its document sent; `deckit-sdk/deckit/listener` stands beside them, as do `connect`'s and `attach`'s once (`connected`, `attached`); on a page, the kit's parts that follow its one document and the overlay beside it (what floats over it, the pointer it captures, its lists, its motion and the kit's stylesheet, in `deckit-sdk/shell/ui`) and `deckit-sdk/match/ranker.js`'s one worker, in the mod's bundle. A page runs one kit and one ranker.

A concept's sides are named for where they run: `main.js` only in main, Electron's process, and `renderer.js` only on a page. Any other file is a part of its concept and runs wherever what imports it runs; a concept not split in sides is usually reached by `index.js`. `protocol.js` is how its own sides reach each other and nobody else's, and what its sides share otherwise is `model/`. A folder is a module (its files and `model/`) or a group (folders only, `model/` not among them); a package's root is a group that also holds `package.json`, `main.js` and `renderer.js`.

Each bundle is its entry and what it imports, through and through, bundled by esbuild: `main.js` and `shell-main.js` (CommonJS, for main) from `deckit-electron/main.js` and `deckit-shell/main.js`, `renderer.js` and `shell-renderer.js` (one global each, for a page's preload) from `deckit-electron/renderer.js` and `deckit-shell/renderer.js`. A package's bundle carries its own copy of what it imports of another. `deckit check`, which the build runs first, holds every file of deckit-electron, deckit-shell and deckit-sdk to the rules above: every file a script, a package depending only on those it may (deckit-sdk on none, deckit-shell on deckit-sdk alone, deckit-electron on deckit-shell and deckit-sdk, so the shell knows no environment), inside deckit-sdk, `deckit/` using none of its other folders, `shell/` and `web/` only `deckit/`, and `match/` and `path/` none, a mod linking only those two and the SDK resolving with no condition only to them, deckit-shell and the SDK's owners' folders free of Electron (nothing required, nothing its bundles carry requiring Electron, no `process`, `globalThis`, `eval`, `module` or `Function(`, and no Electron object's name or member in its code, read with its strings and comments left out but what a template puts in, nor one read in brackets or destructured; `View` and `screen`, a page's words too, only in what its main bundle carries), all an environment's bundles carry of the shell plain declarations and pure functions (nothing required, nothing of a process or a page, no state: no binding assigned again, nor one made by a call, `new` or a literal but what `Object.freeze` makes), only the entries of a package its `package.json` depends on, every folder's import inside or beside it and never above, no package of npm imported or required, no `Deckit` global reached, Electron's IPC reached by none, no channel named outside its concept, a `protocol.js` imported only at its own path below a package's root, and every channel the package's whose `main.js` answers it there, written out as text and declared once, no cycle, what each bundle carries running where the bundle runs (`main.js` only in main, `renderer.js` only in a renderer, Node only in main), every file in a bundle, every folder a module or a group. Deckit.app and the mods are held only to the built bundles and the runtime contract: the build bundles each mod from its own `src/`.

## 7. One design system

The kit is the shell's, and the one way things look and behave in every page it draws (UI.md):

- One token, derived from the host app's theme and the person's fonts: colours, type, radius, shadow, motion, and a code palette. The kit's stylesheet and every mod read it.
- One stylesheet: hover, press, focus and selection are the platform's states, drawn by rules.
- One overlay: a page's layers are drawn in it, over everything laid with the page, each over those added before it, taking presses where they draw. What is presented on them (a menu, a popover, a modal, a drag) is one stack that owns the press outside, Escape and placement.
- One list: rows drawn by key, so what the pointer rests on and what has the focus stay put; one listbox for a list with a cursor, and one tree for the keys of a list or a tree whose items the person selects.
- One shape for each kind of part: a maker takes one options object and returns `{ element, ...its controls }`, a decorator takes an element and returns its dispose, and a control draws the value it is set to and reports what was asked.

## 8. Data

- A rename renames everything, stored keys and channels included. A record's shape is its owner's, and nothing reads an old shape: data written in one is the consumer's to write again.
- A file of a mod's data edited by hand is read at the next start.

## 9. Where the build falls short of the spec

A rule of the spec that this build does not keep, and why. Each is WebKit's: what it lets a host set of a page.

- WebKit hit tests a move with no button held only in a page it counts active, and it counts a page active only while the page's window has the machine's keyboard. The desktop's windows are views in the host window, so a seat's move over a page is heard while the host window has the machine's keyboard, and not while another app or an overlay window has it. The app `deckit test` and `deckit conformance` run never has it, so the cases of [seats at the desktop](../spec/DECKIT-39/SPEC.md) on a move with no button held fail there.
